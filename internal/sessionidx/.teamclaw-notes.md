## #5731 (addPostings 212MB single-site, instance inuse 1675->2225MB, 2026-11-17)
- Root cause: the in-memory posting store was map[string][]Posting - every
  (trigram, line) posting carried a 24B copy of the line's
  Offset/Length/Role/TsNano. Measured pre-fix: 24.67 B/posting retained
  (284k-posting corpus); the memstats top site addPostings+0x3cf held
  212MB / 1337 live []Posting backing arrays (~159KB each).
- Fix: adopt the v2 GROUPED shape in memory (the same 8x win the disk
  format measured in #5149): Index now holds triID map[string]uint32,
  posts map[uint32][]uint32 (trigram id -> line ids, 4B per posting),
  lines []lineRec (metadata once per line; TriIDs nil in RAM). addPostings
  became a method assigning lazy line ids; Query reads lines[lid] for Hit
  metadata; groupedLocked rebuilds the line-major form only transiently at
  save; Load consumes Dict/Lines into the grouped store (legacy
  Version==2-with-Trigrams payloads convert once).
- Size() KEEPS the 40B/posting basis on purpose: it is the budget's
  counting unit, so caps trip at the same posting counts as before -
  behavior unchanged, real heap ~5x lower (measured 4.92 B/posting).
- Pins: zz_issue5731_test.go (memory bound <=12B/posting, roundtrip+tail+
  metadata, legacy-map conversion, duplicate-TriIDs dedup, truncation
  rebuild, capped-drop). Compile-fails pre-fix (ix.triID undefined) - the
  strongest fix pin. Pre-fix control measured via /tmp harness.
- Discovered wart (NOT fixed here, out of scope): Query's multi-hit order
  is map-iteration random; the trailing reverse is cosmetic. Order-sensitive
  tests must assert hit SETS, not sequence.

## #5710 (1-3.3GB heapInuse on fresh instances, 2026-11-16)
- Root cause: Manager.SetLiveID (the path EVERY new interactive session
  takes via agent.SetSessionID -> safego.Go setLiveID) loaded/built the
  live-session index WITHOUT SetSelfBudget - only Start() applied it
  (resumed sessions). Uncapped postings grew to addPostings=471MB/159MB
  per instance (memstats topSites evidence), explaining the NEW-vs-legacy
  split in the issue.
- Second gap found while pinning: Refresh's per-line budget gate runs
  BEFORE each line only - a refresh whose LAST line crosses the budget
  ends over-cap yet UNCAPPED until the next 30min tick. Post-loop
  re-check added; capped refresh now also DROPS partial postings (a
  capped index serves no queries - the map was pure dead heap).
- TailMissingSources: budget applied + MaxIndexableSourceBytes gate
  (budget/40 raw source bytes) skips sources whose build is guaranteed
  to end capped (capped builds never persist -> retry churn).
- idx files live under <sessionsDir>/idx/<id>.idx - tests must join the
  idx/ subdir (zz_issue5710_test.go initially checked dir/<id>.idx).
